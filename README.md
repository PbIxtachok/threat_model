## Цель проекта

Целью проекта не является создание полноценного генератора модели угроз информационной безопасности, а скорее создание шаблона который в любом случае необходимо будет обогащать собственными данными. Однако, на мой взгляд, данный сервис позволяет сэкономить время за счет отдачи самой ресурсоемкой части анализа модели угроз в руки языковых моделей.

Основной задачей при создании проекта была проверка теории возможности поэтапной генерации объемного документа и получение навыков использование языковых моделей с различным числом параметров, в том числе с использованием LLM (локальных языковых моделей). При использовании LLM на одной видеокарте уровня Nvidia P40 с 24 GM VRAM генерация документа в среднем занимает от 6 до 12 часов. При использовании облачных языковых моделей это время снижается до трех часов (в зависимости от используемого сервиса). 

Для ускорения процесса возможно использования балансировщика (например LiteLLM) который позволит распределить задачи по генерации.

## Общее описание
Сервис автоматического формирования документа **«Модель угроз безопасности информации»**
по [Методике оценки угроз безопасности информации ФСТЭК России от 05.02.2021](https://fstec.ru/dokumenty/vse-dokumenty/spetsialnye-normativnye-dokumenty/metodicheskij-dokument-ot-5-fevralya-2021-g)
и [приказу ФСТЭК России № 21](https://fstec.ru/dokumenty/vse-dokumenty/prikazy/prikaz-fstek-rossii-ot-18-fevralya-2013-g-n-21).

Ключевая идея: **структура документа и таблицы собираются программно из
структурированных данных профиля и справочников Методики, а LLM дополняет каждый
смысловой раздел связным текстом и выполняет аналитические задачи** (оценка
применимости УБИ, сопоставление с тактиками, сценарии реализации угроз, тексты
разделов 1, 2, 4, 5, 6, 7). Нормативные документы не подаются в контекст модели
целиком, объём одного запроса к LLM ограничен — сервис работает и с локальными
моделями.

## Возможности

- Заполнение профиля ИС в веб-интерфейсе: реквизиты, классификация (УЗ/класс ГИС),
  обрабатываемая информация, компоненты, интерфейсы, пользователи, негативные
  последствия (табл. 4.1), нарушители (табл. 6.1 с уровнями Н1–Н4 по табл. 8.1);
- сохранение/загрузка/импорт профилей (JSON);
- **автосинхронизация флагов в панели «Интерфейсы и каналы»**: отметки
  «Интернет», «Удаленный доступ», «Wi-Fi/беспроводные сети» и
  «API (внешние интеграции)» автоматически включают соответствующие булевы
  флаги профиля (`has_internet`, `has_remote_access`, `has_wireless`,
  `has_external_integrations`) — именно они учитываются правилами при оценке
  актуальности УБИ. Синхронизация работает и в интерфейсе (в реальном времени),
  и при генерации/сохранении профиля (`sync_interface_flags`). Флаги только
  включаются: ручное включение флага без отметки интерфейса сохраняется;
- **готовые примеры профилей** (см. раздел «Примеры профилей» ниже) — доступны
  в списке «Сохранённые профили» сразу после установки;
- выбор LLM: **Ollama**, **любой OpenAI-совместимый API** (LM Studio, vLLM, llama.cpp),
  **Anthropic Claude**, локальный **transformers** (in-process), **mock** (тест без LLM);
- генерация по этапам с **чекпоинтами**: остановка в любой момент и продолжение
  с места остановки (готовые этапы и уже обработанные батчи УБИ не пересчитываются);
- кэш ответов LLM (повторная генерация того же профиля почти мгновенна);
- выбор применяемых СЗИ/СКЗИ **списком из справочника** (с возможностью вписать
  своё средство) и признак «Применяются СКЗИ» — при их наличии в ИСПДн в документ
  добавляются блок по приказу ФСБ № 378 (подраздел 7.3) и приказ включается в
  перечень НПА раздела 1;
- итог — **DOCX** со структурой: титульный лист, 7 разделов, 5 приложений.

## Быстрый старт

```bash
pip install -r requirements.txt
python app.py
# интерфейс: http://localhost:7860
```

Проверка без LLM: на вкладке «Настройки LLM» выберите провайдер **Mock** в обеих
панелях, сохраните настройки и запустите генерацию — получите тестовый DOCX за секунды.

### Локальная LLM (рекомендуется Ollama)

```bash
ollama pull qwen2.5:14b-instruct   # или другая модель с хорошим русским
# в настройках: провайдер Ollama, адрес http://localhost:11434
```

LM Studio / vLLM / llama.cpp server: провайдер «OpenAI-совместимый API»,
адрес вида `http://localhost:1234/v1`.

### Облачный Claude

Провайдер «Anthropic Claude», укажите API-ключ и модель (например `claude-sonnet-4-5`).

### Провайдер transformers (как в исходной версии)

```bash
pip install -r requirements-local.txt   # ставит torch/transformers (тяжёлые)
```

## Две конфигурации LLM

На вкладке «Настройки LLM» задаются **две независимые конфигурации**:

- **🔍 LLM для анализа УБИ (разделы 7.1–7.2)** — аналитические JSON-задачи:
  оценка применимости УБИ и сопоставление с тактиками. Здесь важны стабильный
  JSON-вывод и max_tokens ≥ 4096 (ответ на батч УБИ длинный);
- **✍️ LLM для текстов разделов (разделы 1–6, сценарии)** — генерация связных
  текстов документа и сценариев реализации угроз. Здесь важны длинные связные
  тексты и большое контекстное окно (16k+); сюда можно указать более сильную
  внешнюю/облачную модель, даже если анализ выполняется локально.

Зачем разделять: локальная модель среднего размера обычно справляется с
дисциплинированными JSON-ответами, но пишет слабые тексты — а длинные тексты
разумно поручить более мощной (например, облачной) модели. Если обе
конфигурации одинаковые, сервис ведёт себя как раньше: при отсутствии
text-конфигурации для текстов используется analysis-конфигурация (полная
обратная совместимость, в том числе со старым плоским форматом
`output/llm_settings.json`).

## Использование Методики ФСТЭК (RAG-lite)

Текст Методики оценки угроз лежит в `data/methodology.txt`. Сервис применяет
гибрид «промпт-пак + лёгкий BM25-RAG» без новых тяжёлых зависимостей
(BM25 — готовый, из `tm_core/retrieval.py`):

1. `tm_core/methodology.py` режет текст на фрагменты по заголовкам
   (строки с префиксом `## `), склеивая мелкие до ~1500–2500 символов;
2. при каждой LLM-генерации текста раздела или сценария из текста задачи и
   ключевых слов профиля формируется запрос, по которому BM25 подбирает до 4
   наиболее релевантных фрагментов (не более 4500 символов);
3. выдержки добавляются в промпт справочным блоком «для терминологии и
   структуры; не цитировать дословно».

Файл `data/methodology.txt` можно **заменить** (например, актуализированной
версией Методики) или **удалить** — в этом случае промпты работают как раньше,
без выдержек (в лог пишется info-сообщение).

## Требования к LLM

LLM в сервисе не «украшение», а рабочий инструмент: она оценивает применимость
угроз БДУ ФСТЭК к конкретной системе, сопоставляет актуальные угрозы с техниками
реализации и пишет связные тексты содержательных разделов документа. Поэтому к
модели предъявляются минимальные требования:

- **instruction-tuned модель** с уверенным русским языком (base-модели без
  instruct-дообучения не подходят);
- **контекстное окно ≥ 8192 токенов** (рекомендуется 16 384 и более) — в запрос
  входят расширенный профиль объекта и описания УБИ/техник;
- **стабильный JSON-вывод** (поддержка JSON mode / `response_format` желательна) —
  результаты оценки УБИ и тактик запрашиваются строго в JSON;
- **max_tokens ответа ≥ 4096** — при меньшем лимите JSON-ответ на батч УБИ
  обрезается и угрозы помечаются как «без ответа LLM»;
- рекомендовано: **Qwen2.5-14B/32B/72B-Instruct**, **GPT-4o-mini** и выше,
  **Claude Sonnet**; допустимо с оговорками: модели **7–8B instruct**
  (ставьте «УБИ в одном запросе» = 1–2, будет больше повторных попыток);
  **не рекомендуются**: модели меньше 7B и base (не instruct) модели.

При недоступности или отказе LLM конвейер не падает: текстовые разделы
остаются шаблонными, а неоценённые угрозы помечаются `llm_error` с пометкой
«Оцените применимость вручную» и переобрабатываются при следующем запуске.

## Примеры профилей

В каталоге `data/sample_profiles/` поставляются четыре готовых примера профилей,
которые при первом запуске автоматически копируются в `output/profiles/` и сразу
доступны в выпадающем списке «Сохранённые профили» (вкладка «1. Профиль ИС»).
Они служат шаблонами: откройте пример, скорректируйте под свой объект и сохраните
под новым именем. Уже существующие файлы в `output/profiles/` при повторных
запусках не затираются — ваши правки сохранятся.

- **ИСПДн_Платежный_сервис** — информационная система обработки платежей и ПДн
  (уровень УЗ-1, применяются СКЗИ);
- **ЗО_КИИ_Электросети** — АИС управления электросетевым хозяйством, значимый
  объект КИИ (класс К2, ViPNet);
- **АСУ_ТП_Котельная** — АСУ ТП газовой котельной (изолированный контур, без
  подключения к Интернет);
- **ГИС_Портал_госуслуг** — ГИС «Портал госуслуг» (класс К2, размещение в
  государственном облаке).


## Архитектура

```
threat_model_service/
├── app.py                  # веб-интерфейс (Gradio), фоновые задания + gr.Timer
├── tm_core/                # ядро (не зависит от UI)
│   ├── schema.py           # Profile, JobState, порядок этапов
│   ├── dictionaries.py     # загрузка справочников и датасетов
│   ├── providers.py        # абстракция LLM (Ollama/OpenAI/Claude/transformers/mock)
│   ├── retrieval.py        # лёгкий BM25 (вместо langchain+FAISS+эмбеддингов)
│   ├── methodology.py      # RAG-lite по тексту Методики ФСТЭК (BM25)
│   ├── analysis.py         # правила + LLM: применимость УБИ, тактики, тексты разделов
│   ├── intruder_logic.py   # уровни Н1–Н4, сговор, актуальность нарушителей
│   ├── storage.py          # профили, черновик, настройки LLM, задания, кэш
│   ├── pipeline.py         # конвейер этапов s1–s9 с возобновлением
│   └── docgen.py           # сборка DOCX (python-docx)
├── data/
│   ├── ubi.csv             # УБИ из БДУ ФСТЭК (227 шт.)
│   ├── threat_list.csv     # тактики/техники Т1–Т10
│   ├── methodology.txt     # текст Методики ФСТЭК для RAG-lite (можно заменить/удалить)
│   └── dictionaries/       # извлечённые таблицы Методики (4.1, 6.1, 8.1 и др.)
│                           # + security_tools.json — справочник СЗИ/СКЗИ (пользовательский)
├── tests/test_pipeline.py  # сквозной тест: профиль → DOCX + тест возобновления
└── output/                 # профили, задания, кэш (создаётся при работе)
```

### Этапы конвейера

| Этап | Раздел документа | LLM |
|------|------------------|-----|
| s1 | 1. Общие положения | да (вводный текст о цели документа) |
| s2 | 2. Описание системы | да (тексты подразделов 2.1–2.4) |
| s3 | 3. Негативные последствия | да (обоснование выбора рисков) |
| s4 | 4. Объекты воздействия | да (обоснование объектов и видов воздействия) + правила |
| s5 | 5. Источники угроз | да (обоснование нарушителей и уровня) + правила Методики |
| s6 | 6. Способы реализации | да (связный текст о способах) + справочник тактик |
| s7 | 7.1. Актуальные УБИ (+7.3. Класс СКЗИ, если применимы) | да (батчи + ретраи + правила-префильтр + partial-чекпоинты, вводный и итоговый тексты) |
| s8 | 7.2. Сценарии (УБИ × тактики) | да (BM25 shortlist + батчи с ретраями + сценарии реализации) |
| s9 | Сборка DOCX | нет |

Все LLM-тексты опциональны: при ошибке LLM этап не падает, раздел остаётся
шаблонным.

Состояние задания: `output/jobs/<job_id>/state.json`; результаты этапов — `<этап>.json`;
прогресс внутри LLM-этапов — `<этап>.partial.jsonl` (дозапись после каждого батча).
